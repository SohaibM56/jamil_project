# Jamil Project

Digital business card app. A user builds a profile ("card") with contact info and
social links, then shares it via a QR code / URL that opens a **public, no-login
web page** showing that card — the classic "Linktree for your business card" idea.

## Stack

- **App:** Flutter, GetX (state management, DI, routing). See [README.md](README.md)
  for the current folder structure and MVVM conventions.
- **Backend:** Firebase.
  - **Firebase Auth** — email/password sign-in. Implemented in
    `AuthRepository` ([lib/src/repos/auth_repository.dart](lib/src/repos/auth_repository.dart)).
  - **Firestore** — stores user accounts and public card data. Schema in
    [docs/firestore_schema.md](docs/firestore_schema.md). Security rules live
    in [firestore.rules](firestore.rules) (not yet deployed — run
    `firebase deploy --only firestore:rules` when ready). Card reads/writes go
    through `CardRepository`
    ([lib/src/repos/card_repository.dart](lib/src/repos/card_repository.dart)),
    modeled by `CardModel`/`CardLink`
    ([lib/src/models/card_model.dart](lib/src/models/card_model.dart)).
  - **Firebase Storage** — avatar images, one fixed object per user at
    `avatars/{uid}` (re-uploads overwrite in place, so Storage cost doesn't
    grow per edit). Wrapped by `StorageRepository`
    ([lib/src/repos/storage_repository.dart](lib/src/repos/storage_repository.dart)).
    Rules in [storage.rules](storage.rules) (not yet deployed — run
    `firebase deploy --only storage` when ready).
  - **Firebase Hosting** — serves a static React SPA (separate codebase, not in
    this repo) at the domain the QR code points to. That page reads a card ID
    from the URL and renders the public card straight from Firestore — the
    Flutter app is never involved in viewing someone else's card.
- Firebase SDKs (`firebase_core`, `firebase_auth`, `cloud_firestore`,
  `firebase_storage`) are in `pubspec.yaml` and initialized in `main.dart` via
  `firebase_options.dart` (generated by the FlutterFire CLI).

## Logical flow

**Splash**
- `main.dart` inits Flutter bindings and calls `Firebase.initializeApp()`
  before `runApp`.
- `SplashController` waits briefly, checks auth state via
  `AuthController.isAuthenticated` (backed by
  `FirebaseAuth.instance.currentUser`), then routes to Dashboard or Login.

**Auth**
- **Signup:** create the Firebase Auth user → batch-write `users/{uid}`
  (private) + `cards/{cardId}` (public, new random ID) → mark authenticated →
  Dashboard. Implemented in `AuthRepository.signup()`.
- **Login:** sign in with Firebase Auth → mark authenticated → Dashboard.
  Wired through `LoginController.login()` → `AuthController.login()`.
- **Forgot password:** Firebase Auth password-reset email, wired through
  `ForgotController.resetPassword()` → `AuthController.forgotPassword()`.
- **Logout:** Firebase Auth sign-out → back to Login.
- **Route guard:** `AuthMiddleware` in
  [app_router.dart](lib/src/config/app_router.dart) keeps unauthenticated users
  out of the dashboard and authenticated users out of the auth screens.

**Dashboard** (bottom nav: QR / Account / Links / Settings)
- All four tabs share one `DashboardController`
  ([lib/src/mvvm/viewModels/dashboard_controller/dashboard_controller.dart](lib/src/mvvm/viewModels/dashboard_controller/dashboard_controller.dart)),
  which resolves `cardId` once per session (`users/{uid}.get()`) and opens a
  single `cards/{cardId}` `onSnapshot` listener for the lifetime of the
  session — switching tabs never re-queries. Every write is a targeted
  dot-path `CardRepository.update()` call (e.g.
  `'links.instagram.visibleOnCard'`), never a whole-doc overwrite, and nothing
  re-fetches after writing — the shared listener already reflects it.
- **Account tab:** shows the card (name, title, phone, email, avatar) read
  live from `dashboardController.card`. The avatar's own edit icon opens a
  camera/gallery picker
  ([avatar_source_dialog.dart](lib/src/widgets/avatar_source_dialog.dart)),
  uploads via `StorageRepository`, then writes the download URL to
  `profileImageUrl` — reflected instantly in Settings too since both tabs read
  the same live model. The other edit icon opens the existing combined
  name/title/phone dialog
  ([edit_card_dialog.dart](lib/src/widgets/edit_card_dialog.dart)), now
  writing to Firestore via `DashboardController.updateAccountInfo`. Per-link
  visibility toggles are disabled until that platform has a URL configured
  (can't make a link visible with nothing behind it).
- **Links tab:** add/remove a URL per social platform via
  `DashboardController.upsertLink`/`removeLink`, unified into the single
  `links.{platform}` map the schema always intended (previously three
  disagreeing local maps — see Known issues history).
- **QR tab:** renders a QR code encoding the real
  `https://<hosting-domain>/#/{cardId}` URL, `cardId` resolved from the shared
  controller (was hardcoded to a fake ID).
- **Settings tab:** name/title read from the same live `cards/{cardId}` model;
  title is editable via a dedicated title-only dialog
  ([edit_title_dialog.dart](lib/src/widgets/edit_title_dialog.dart)) →
  `DashboardController.updateTitle`. Privacy/terms are still stubs.
  **Logout** and **delete account** are real: `AuthController.logout()` signs
  out of Firebase Auth; `AuthController.deleteAccount()` (behind a
  confirmation dialog) deletes the `users/{uid}` + `cards/{cardId}` docs and
  the Firebase Auth user itself — implemented in
  `AuthRepository.deleteAccount()`.

**Public card page (Hosting, not this repo)**
- Visitor scans the QR / opens the link → static React page reads `cardId` from
  the URL → reads `cards/{cardId}` directly from Firestore (public read rule,
  no auth) → renders name/title/avatar + only the links marked visible, each
  linking out to the real platform URL.
- Unknown/deleted `cardId` → simple "this card isn't available" state.
- This is the entire point of the QR flow: the *owner* edits their card inside
  the Flutter app, but anyone can *view* it on the web with no account.

## Commands

- `flutter pub get` — install dependencies.
- `flutter run` — run the app.
- No code generation step today (no Freezed/Riverpod, despite what older docs
  said) and no test suite exists yet.
